1. The architecture, in one paragraph

Four systems in one Cloudflare Worker plus a chip client. The wallet (passkey login = passkey signer of a MetaMask HybridDeleGator on Arc) grants a budget to a robot's chip address as a delegation with caveats (daily cap, per-payment cap, payee allowlist, expiry, approval requirement). The Robot Agent (an Effect service with D1 state, one errand at a time per robot) asks 0G for a structured decision, hands the invoice to the chip over HTTPS long-polling, and submits the chip-signed voucher to the merchant's x402 endpoint; our facilitator simulates and settles it through the DelegationManager, and Arc checks every caveat. Restricted or over-cap purchases need a World Agent Pass approval that the backend verifies and co-signs. Every decision is logged with its 0G request id and uploaded to 0G Storage. Diagrams: the architecture page. Build detail: docs/spec.md.

5. Alternatives considered and rejected

  • World Chain + 0G + ENS instead of Arc: no World Chain prize; MetaMask's delegation contracts aren't on World Chain; gas in ETH; World's wallet can't grant allowances. ENS names could sit on top of Arc later (docs/research/worldchain-ens-alternative.md).
  • The float path (pull to the chip, then EIP-3009 via Circle): after the pull, Arc no longer binds payee, invoice or revocation. Later fix: a policy-bound escrow.
  • Verifying the World token on Arc by default: publishes the owner's World pseudonym in calldata. Stretch only.
  • An Agents SDK / Goblin-style agent, WebSockets and MCP between our own components: don't compose with the Effect/Alchemy foundation and add hours without adding security.
