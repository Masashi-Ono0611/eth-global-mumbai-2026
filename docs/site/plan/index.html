0.8 Design gaps found in the review (fixed below)

  1. The float path would bypass the merchant allowlist. The chip can pull to itself and then pay any seller. Fix: the pull uses its own small cap (e.g. $1/day float budget). Float is a stretch anyway.
  2. How does Arc know an item is restricted? Fix: approval is required when amount > perPaymentCap or the payee isn't on the grant's allowlist. The merchant sends restricted items to a separate payTo address that owners never allowlist, so they always need Agent Pass.
  3. Two ways to submit a payment (wallet MCP payment_submit vs the x402 header to the merchant). Fix: robot payments go through x402 to the merchant only. The wallet MCP keeps balance/history, approval_request and grant_change_request. The chip already stores its grant (bench C1), so it builds the leaf itself.
  4. x402 header size (≈ 12 KB permission context, more with a World token). Uncertain: test it against the Worker in S2's envelope test; trim caveats first.
  5. No map of the apps. Fix: one web app with three parts: wallet (owner), robot console (camera, control, decision log) and merchant (store and checkout page). The ESP32 is the gate.
  6. Eligibility: "from scratch" and "large single commits may be disqualified". Fix: README disclosure (0.5); all product code lands as small commits from now on.

1. The shape

# System What it is
1 Wallet (foundation) Passkey signup (HybridDeleGator on Arc), fund, send, receive, grants to any address, an MCP server whose OAuth consent creates a grant, Agent Pass approvals. No Privy-style services. Prior art: Nod
2 Robot Agent One Cloudflare Durable Object per robot = the AI client. It calls 0G, holds the wallet MCP connection, runs the plan/act loop, logs every decision, and talks to the chip over a WebSocket the chip opens. It runs with no chip (headless or sim). Goblin-inspired, robot-specific
3 Merchant Store config (items, USDC prices, rules: needs approval / restricted), x402 checkout accepting both payment paths, and later the ESP32 gate
4 Chip The robot's body and signer: the Radxa (real) or a mock chip (a Bun process, iteration 1). It holds the key the grant is delegated to and signs every robot payment. Camera and motors on the real one

The Grant (unchanged core)

Grant   = signed MetaMask Delegation Framework delegation: owner account → chip address
          caveats: USDC only (AllowedTargets/Methods), ValueLte(0), period cap, expiry,
                   + ours: RobotPaymentPolicyEnforcer (per-payment cap, merchant allowlist, a small separate float cap
                           for pulls to the chip itself),
                           HumanApprovalEnforcer (Agent Pass approval required when amount > per-payment cap OR the payee
                           is not on the allowlist; restricted items use a merchant payTo that is never allowlisted)
Payment = the chip signs a one-time leaf (exact USDC.transfer(payee, amount), IdEnforcer(invoiceHash), Timestamp);
          a facilitator calls redeemDelegations; Arc checks every caveat.
Owner action = the passkey signs a one-time delegation to the relayer (send, revoke, add passkey).
  • Known: the grant chain was simulated on live Arc mainnet state (wallet-accounts-v2.md A1–A7).
  • Passkey-native is still a DeleGator. "DeleGator" is MetaMask's name for their smart accounts that can create and redeem delegations:
    • our owner account is a HybridDeleGator: its own contract, its own address, the passkey as signer
    • the 7702 fallback is an EOA whose code points to EIP7702StatelessDeleGator
    • both use the same DelegationManager and caveats

2. System by system

2.1 Wallet

The wallet design is unchanged from v2, except for owner actions and approvals:

  • Account: passkey-native HybridDeleGator via SimpleFactory, live on Arc. Decided (D1).
    • Uncertain: real-device passkeys (S1).
  • Signup: our relayer deploys the account (≈ $0.005).
  • Funding: USDC on Arc; other chains via CCTP or Gateway. "Connect MetaMask" means a funding source, or an extra signer.
  • MCP server: workers-oauth-provider + createMcpHandler (for the event the Robot Agent is the only client; outside hosts like claude.ai are cut). The OAuth consent page is the grant ceremony: it shows the robot's name and chip address and the budget; the passkey signs.
  • Raising a budget: the agent calls grant_change_request, which returns a link (or an in-chat prompt where the host supports it). The owner opens the wallet and the passkey signs a new grant.
  • MCP tools (review fix: robot payments go over x402 to the merchant, never through the wallet MCP; the chip stores its grant and builds the leaf itself, as in bench C1):
    • wallet_overview, payments_list, payment_status
    • approval_request (Agent Pass for one payment), grant_change_request (raise the budget)
    • stretch: float_pull (exact-amount pull to the chip, capped by the float cap)
  • Owner actions (decision H): the passkey signs a one-time delegation and our relayer (the facilitator code) submits it (≈ $0.006).
    • Break-glass: if MetaMask pauses the DelegationManager, an ERC-4337 v0.7 user operation via Pimlico's public bundler, with gas paid by the account in USDC from its own balance. HybridDeleGator v1.3.0 uses EntryPoint v0.7.
    • Other chains (gas isn't USDC): 4337 + a USDC paymaster, as in Goblin ADR 0050.
    • Trust: signatures bind exact actions and caps are on-chain, so no relayer or bundler can steal or redirect funds; at worst they delay.
    • Self-hosted bundler: no. No public Arc RPC exposes debug_traceCall; only paid Alchemy or our own node do.

2.2 Robot Agent (iteration 1 headless, iteration 2 with the chip)

  • Runtime: a Cloudflare Agents SDK Agent, one per robot, with schedule for timeouts and wakes. Copy from Goblin (~/code/goblin/apps/runtime/src/):
    • agent.ts: the Agent + schedule pattern
    • pi/model.ts: pi-ai openai-completions pointed at the 0G router. Add the onResponse hook to capture 0G request ids, which Goblin doesn't do yet
    • mcp/oauth/oauth-provider.ts + mcp/oauth/auth.ts: the MCP OAuth client
    • mcp/approvals/*: hold the exact call, end the turn, continue on approval
    • telemetry/pi.ts: append-only run events (evidence)
  • Not copied: personas, topics, subagents, apps, inbound MCP, the AG-UI shell, Effect layers.
  • 0G: standard providers (decision E), with the teammate's credits.
    • Uncertain: which tool-calling model, ideally with images (glm-5.3-flash / qwen3.8-flash), and latency (S3).
    • If 0G fails, the step takes no action. That's the prize's safe-stop.
  • Pairing (decision B):
    1. The owner adds a robot in the wallet and gets a pairing code.
    2. The chip (real or virtual) generates its key, opens a WebSocket to its Robot Agent with the code, and proves its address by signing a challenge.
    3. Only then does the Agent connect to the wallet MCP. The consent screen shows "Vitaquack (0xChip…) wants $10/day", and the grant's delegate is the chip address.
  • Paying (decision C):
    1. The Agent decides on 0G and fetches the merchant's x402 requirements.
    2. It sends the invoice to the chip, which builds the leaf from its stored grant.
    3. The chip checks the invoice (on the real chip, one it scanned itself) and signs.
    4. The Agent submits.
    • The Agent never holds a spending key.
  • Body: camera frames (JPEG over the chip's WebSocket, fanned out to browsers while someone watches) and movement (move {vx,vy,vyaw}, 300 ms deadman, owner e-stop, human beats AI). From robot-browser-and-mcp.md.
  • No simulator (dropped): iteration 1.5 is a virtual x402 resource instead.

2.3 Payments: grant + float (decision C)

Grant path Float path
For Our merchant (accepts ERC-7710) Any x402 seller that only takes EIP-3009
How Chip signs a one-time leaf → our facilitator → redeemDelegations The chip pulls the exact amount (a grant payment to itself: ExactCalldata(transfer(chip, amount)), IdEnforcer(invoice)), waits for the receipt, then signs EIP-3009 (validBefore ≤ 120 s) → Circle's Facilitator Service
Limits enforced All of them, on Arc, at payment time All of them at the pull, plus a separate small float cap (review fix: otherwise the chip could pull to itself and pay any seller, bypassing the allowlist); the seller payment itself is a plain transfer
Cost 1 tx: ≈ 663k gas ≈ $0.013 measured in spike S2 (≈ 505k / $0.010 with redundant caveats dropped; the passkey check and ~13 caveats dominate) 2 txs, about 1 s on Arc, invisible to the user
On failure Revert: nothing paid Let the authorization expire (or call cancelAuthorization), then sweep the float back to the owner
  • Our facilitator:
    • Known: no shipping open-source ERC-7710 facilitator exists. x402 PR #1837 is a stalled draft; MetaMask's facilitator is hosted on Base and Monad only.
    • So we write ~150 lines with viem, from references/danfinlay_x402@7710-implementation (PR #1837) and references/fireblocks_x402-facilitator (Erc7710Mechanism.ts: DelegationManager allowlist, packed calldata).
    • Simulate with account: relayer, or the Redeemer caveat fails.
  • Circle's Facilitator Service (Known, live check):
    • base URL https://api.circle.com/v1/facilitator/x402, x402 v2, eip155:5042 with exact (+ upto)
    • auth: API key, or the keyless Facilitator-Seller-Proof (an EIP-712 signature by the payTo)
    • payer may be an EOA or a deployed ERC-1271 account; Circle pays gas; both sides are sanctions-screened
  • Our merchant lists both in accepts[], EIP-3009 first, because stock clients take accepts[0]. One routing facilitator client sends authorization payloads to Circle and permissionContext payloads to ours.
  • Prior art: Goblin's archived wallet (tag hackathon-2026-10, ADRs 0045/0050) did ERC-7710 period allowances with just-in-time top-ups and x402/MPP on Base. Coinbase Sub Accounts' auto-spend (references/base_account-sdk) does the same pull-then-pay.
  • MPP later (decision D): Circle's USDC MPP method is EIP-3009 and works on Arc by chain id (references/tempoxyz_mpp-specs, references/wevm_mppx). It would reuse the float path.

2.4 Merchant

  • Store config: items, USDC prices, flags needsApproval / restricted, and a payout account.
  • Checkout: x402 v2 with both entries in accepts[], plus payment-identifier (idempotency).
  • Invoice binding: IdEnforcer(invoiceHash). One receipt is final.
  • Iteration 2: the ESP32 gate keeps the bench-answers.md endpoints:
    • Ed25519-signed status with a gate nonce, verified with Monocypher crypto_ed25519_check
    • a used state, so a cached paid can't reopen the gate
  • Restricted items (the mock cigarette pack) need a fresh Agent Pass approval, not an age proof (see 2.5).

2.5 World: Agent Pass, verified on Arc (decision F, updated)

  • What Agent Pass is: ETHGlobal's name for World IdP, World's OIDC sign-in at auth.world.org.
    • Known: World IdP itself uses no chain. World does have its own chain (World Chain) for its wallet and on-chain World ID proofs, but Agent Pass doesn't touch it.
    • It returns an RS256-signed ID token (JWKS at /.well-known/jwks.json, RSA-2048).
  • Decided: the approval is verified on Arc itself (Kris, 2026-11-05), so our backend is no longer a trusted approver.
    • Flow: World IdP's browser (authorization-code) flow, not the device flow, because only the browser flow accepts a nonce and echoes it into the token. We set nonce = the EIP-712 hash of {invoiceHash, amount, payee, expiry} and use max_age=0 / prompt=login to force a fresh World ID check. The owner opens the approval on their phone from our wallet page, which shows item, amount, payee and invoice. World App itself can't show what is approved.
    • On-chain check: HumanApprovalEnforcer (built in Arc Studio) receives the raw token in the caveat args, RSA-verifies it with OpenZeppelin RSA.pkcs1Sha256 (modexp precompile, ≈ 33k gas) and parses the claims (≈ 100–300k gas; < $0.01 total). It checks:
      • iss, aud, exp, sub = the owner's World pseudonym (stored at setup)
      • nonce = this payment
      • auth_time recent
      • amr contains pop and not mfa (spike S5b: a passkey-only sign-in is ["pop","user","mfa"], so pop alone isn't enough)
      • jti not used before (stored)
    • Remaining trust: World IdP, plus whoever registers World's public key on Arc (a key-admin role; handle key rotation). Arc itself is permissioned proof-of-authority (Circle + about 11 validators).
    • For the 09:00 deadline (D15): the backend co-signer is the default. Our backend verifies the token (same checks) and co-signs EIP-712; HumanApprovalEnforcer checks the co-signature. The on-chain verifier (S5b prototype, 43 tests) is the stretch swap.
  • Deny / cancel: the owner refuses in World App, or never completes it. Then no token exists, so the voucher can't pass the enforcer and nothing is paid.
  • Agent Pass vs the MCP grant: the grant is the standing budget (passkey, in our wallet). Agent Pass is a one-off exception for one over-limit or restricted payment (World App). Raising the budget is a new grant, not Agent Pass.
  • World's wallet can't replace ours: "World Money" is a Safe on World Chain only. World's SDK refuses other chains for transactions, a Safe can't be a Delegation Framework delegator, and World resets allowances after each transaction. A World mini app could at most fund our Arc account (World Chain → Arc via CCTP/Gateway).
  • Setup: register a client at auth.world.org/portal (HTTPS redirect URI, client_secret_basic); sandbox at sandbox.auth.world.org; Kris has an Orb-verified ID.
  • Dropped: the IDKit HumanRegistry / 18+ path. AgentKit (archived, no age).

2.6 Venue network (decision I, updated by bench H4)

  • Bench H4 finding: the venue Wi-Fi is unusable for the robots: about 3 KB/s, pings up to 2.5 s, a 1 MB scp never finished.
  • Primary: a dedicated phone hotspot. Pixel, 2.4 GHz, WPA2, name duckbench, shared by the Radxa, the ESP32 and the laptops. Use its own mobile data (a local SIM) as the uplink.
  • Alternative: macOS Internet Sharing from a wired Ethernet uplink. Settings:
    • channel 1, 6 or 11
    • WPA2/WPA3 (never WPA3-only)
    • Radxa key-mgmt wpa-psk; ESP32 setMinSecurity(WPA2_PSK)
    • run caffeinate -dis
  • Doesn't work: reverse-tethering into the Android hotspot (hotspot clients bypass gnirehtet's VPN).

2.7 ESP32 gate wiring

  • A micro servo (SG90 / MG90S) needs no extra chip:
    • signal to a GPIO (e.g. GPIO 13; 3.3 V logic is fine)
    • power from a separate 5 V supply of at least 1 A, not the ESP32's 3.3 V pin
    • grounds joined
    • a 470 µF capacitor across the servo supply
    • code: ESP32Servo attach(pin, 500, 2400)
  • Powering the servo from the ESP32 over the Mac's USB can brown-out-reset the board. A PCA9685 driver only matters for many servos.
